# 1. Executive Summary

## 1.1 Project Overview

The project turns a single-file Node.js service from a catch-all greeting into a path-routed surface: `GET /good-evening` was added while `GET /` was preserved byte-for-byte, the service moved onto an Express HTTP layer, and a root `package.json` declares that dependency for the first time. It serves two plain-text responses over TCP port 3000, with no accounts, data store or configuration. Scope is two files: `server (1).js` (7 lines) and the manifest. The impact is one additional documented endpoint on an unchanged service, with its boot, readiness and failure behaviour intact.

**The statement's shape.** The plan's illustrative diff hands `.listen` to the Express app itself; the delivered statement makes the app the request listener of a plain HTTP server instead (`server (1).js:5–7`). Express treats a trailing callback as a completion handler *and* installs it as the server's one-time `error` sink, so in the illustrative form a contended bind hands the error to the readiness arrow, which prints the success line, swallows the failure, and the process exits 0 having bound nothing. The delivered shape leaves that callback as a `listening` listener, so a contended start exits 1 with `EADDRINUSE` and prints no readiness line — the behaviour the repository specification requires and Section 4 records. Rewriting the statement to match the illustrative line would reintroduce the silent failure while reporting a successful start.

**The file's documentation.** The plan required the duplicated JSDoc blocks to be left exactly as they stood and treated their stale wording as a deliberate consequence of keeping the diff minimal — the file originally carried four copies of a claim the routed file no longer satisfied. The owner directed that the delivered change be improved without expanding its scope, which cannot be done while a comment misstates what the file does, so the three orphaned copies were removed and the surviving block was replaced by one accurate block (`server (1).js:1,4`). No runtime value moved, and the unused require the same clause protects was left byte-for-byte.

**The undeclared runtime package.** `server (1).js:2` requires `lodash`, and the manifest deliberately declares only `express`. The instruction that `express` be the sole new dependency, combined with the requirement to leave the existing require untouched, makes this a decided state rather than an omission — and the module is genuinely unused, bound to `_` and never referenced again. The practical effect is that the repository is not self-sufficient: `npm install` from the manifest yields a process that exits 1 with `Cannot find module 'lodash'` and never binds. Supplying the package out of band (`npm install --no-save`, which leaves the manifest byte-identical) or declaring it properly both resolve the boot; only declaring it makes the repository complete on its own.

**Reproducibility of the install.** The three-field manifest is the entire committed dependency state: `"express": "5"` is a range, not a release, and no lockfile records what was installed, because the project owner's instruction was to assume the latest stable major line without registry lookups, test installs or measured requests. Two consequences follow. Installs can resolve to different releases, so the framework defaults this guide verifies — the automatic `X-Powered-By` header, the weak `ETag` and its 304 behaviour, case-insensitive and trailing-slash-tolerant matching, and the escaping of the reflected path in the 404 page — belong to whichever 5.x an install resolves. And `npm ci` cannot run at all, because it requires a lockfile. Committing the lockfile an install writes closes both, without adding a field or a second dependency.

**Documentation left behind the code.** `README.md` still tells a reader to install lodash by hand and says nothing about the manifest dependency, and `blitzy/documentation/Technical Specifications.md` still describes a server with no framework, no manifest and no routing. Both were excluded from the change, correctly, since the request permitted edits to one file only. Until they are refreshed the repository's own instructions contradict what ships — and the README line is a trap: run verbatim once a manifest exists, `npm install lodash` saves lodash into the tracked `package.json`, changing the dependency declaration the release fixes. Refreshing both documents, and documenting the `--no-save` form, removes the contradiction.

**Handlers, hardening and the network surface.** The service deliberately has no 404 handler, no error handler, no environment-variable configuration, no TLS, no security headers, no CORS policy and no rate limiting. The framework's defaults fill the gaps: unmatched requests get the stock 404 page with the requested path escaped, `X-Powered-By: Express` identifies the stack, and a plain-HTTP listener accepts anything that can reach port 3000. None of this is reachable by a change the request allowed, and the repository specification already treats the real bind address (`::`) as the requirement, with the loopback text as display only.

**One instance per host.** Port 3000 is a hard-coded literal and the listener binds every interface (`server (1).js:7`), so a second instance cannot coexist on the host: it exits 1 with `EADDRINUSE` and prints no readiness line, which is the intended failure rather than a relocation path. Because the startup text names `127.0.0.1`, an operator reading only stdout can conclude the service is loopback-only while it is in fact reachable on every interface. A configuration surface for both the port and the bind address, with the readiness line reporting the address actually bound, resolves the constraint and the ambiguity together.

# 8. Summary & Recommendations

# 9. Development Guide

## 9.1 System Prerequisites

- **Node.js 18 or newer** — the dependency's own `engines` field requires `>= 18`; this release was built and verified on Node.js v22.23.3.
- **npm 11.x** (verified on 11.21.0). No other package manager is configured.
- **No infrastructure**: no database, cache, message broker, VPN, external endpoint or seed data. The process reads no configuration value at all and boots under an empty environment.
- **Port 3000 free on the host.** The port is a hard-coded literal with no override, so only one instance of this service can run per host.

The file name contains a space and parentheses — always quote it: `node "server (1).js"`.

## 9.2 Repository Layout

```
.
├── README.md                                 # project name, install line, run command
├── package.json                              # name, version, dependencies: { "express": "5" }
├── server (1).js                             # the whole service: two routes plus the listener
└── blitzy/documentation/Technical Specifications.md
```

There is no build step, no source tree, no test runner, no linter and no CI configuration: `server (1).js` is plain CommonJS JavaScript and loads directly.

## 9.3 Dependency Installation

```bash
# from the repository root
CI=true npm install --no-audit --no-fund
```

Expected: the install completes and `express` resolves from the local tree at the declared major line (5.3.0 when this guide was verified).

**Two things to know before you run it:**

1. **The service also requires `lodash`, which the manifest does not declare.** `server (1).js:2` loads it, so a checkout whose only install is the command above exits 1 with `Error: Cannot find module 'lodash'` and never binds. Satisfy it without touching the manifest:

```bash
CI=true npm install --no-audit --no-fund --no-save lodash   # leaves package.json byte-identical
# or point Node at a dependency tree that already contains it:
NODE_PATH=/path/to/a/tree/with/lodash node "server (1).js"
```

2. **The install writes an untracked `package-lock.json`.** This release deliberately commits no lockfile, so keep that file out of commits. Do not add `lodash` to `package.json`, and do not run `npm ci` — it requires a lockfile and exits with `EUSAGE`.

## 9.4 Static Check

```bash
node --check "server (1).js"     # exit 0, no output
node -e "JSON.parse(require('fs').readFileSync('package.json','utf8'))"   # exit 0
```

## 9.5 Starting the Service

```bash
# from the repository root
nohup node "server (1).js" >app.out 2>app.err & echo $! > app.pid
sleep 2
cat app.out
```

Expected stdout, exactly one line (41 bytes) and nothing on stderr:

```
Server running at http://127.0.0.1:3000/
```

The line is printed once the socket is bound. The listener binds every interface on port 3000; the `127.0.0.1` in the message is display text, not the bind address.

## 9.6 Verifying a Running Instance

```bash
curl -sS -o /dev/null -w 'GET /              -> %{http_code} %{content_type} %{size_download}\n' http://127.0.0.1:3000/
curl -sS -o /dev/null -w 'GET /good-evening  -> %{http_code} %{content_type} %{size_download}\n' http://127.0.0.1:3000/good-evening
curl -sS http://127.0.0.1:3000/ | sha256sum
curl -sS http://127.0.0.1:3000/good-evening | sha256sum
curl -sS -I -o /dev/null -w 'HEAD /good-evening -> %{http_code} %{size_download}\n' http://127.0.0.1:3000/good-evening
curl -sS -o /dev/null -w 'unmatched path   -> %{http_code}\n' http://127.0.0.1:3000/no-such-path
curl -sS -o /dev/null -w 'POST /           -> %{http_code}\n' -X POST http://127.0.0.1:3000/
```

Expected results:

| Check | Expected |
|---|---|
| `GET /` | `200 text/plain; charset=utf-8 14` |
| `GET /good-evening` | `200 text/plain; charset=utf-8 13` |
| sha256 of `GET /` | `c98c24b677eff44860afea6f493bbaec5bb1c4cbb209c6fc2bbb47f66ff2ad31` |
| sha256 of `GET /good-evening` | `15827d630bcabd8b6952860d86096076ffbe023080785365150032ab34a8f05c` |
| `HEAD /good-evening` | `200` with `Content-Length: 13` and an empty body |
| unmatched path | `404`, framework error page, no internals |
| `POST /` | `404` |

A second instance started while the first holds port 3000 must exit 1, print **no** readiness line, and report `Error: listen EADDRINUSE: address already in use :::3000` on its stderr:

```bash
node "server (1).js"; echo "exit=$?"     # while another instance holds :3000
```

## 9.7 Stopping the Service

```bash
kill "$(cat app.pid)"
lsof -nP -iTCP:3000 -sTCP:LISTEN || echo "port released"
```

Always stop by the pid you started and never by process name — the name matches every checkout on a shared host.

```bash
$ node "server (1).js" &

$ curl -sS -D - http://127.0.0.1:3000/good-evening

Content-Type: text/plain; charset=utf-8
Content-Length: 13
ETag: W/"d-7fFyiNLFhmJrNT+BforqesSHNow"
```

Behaviour a client should expect from the framework's defaults: queries, trailing slashes and path case are tolerated (`/good-evening/` and `/Good-Evening` return the same body); percent-encoded or dot-segment paths return 404; unmatched paths and non-GET methods return 404; `OPTIONS` returns `Allow: GET, HEAD`; a conditional `GET` with a matching `If-None-Match` returns 304.

## 9.9 Troubleshooting

| Symptom | Cause | Resolution |
|---|---|---|
| `Error: listen EADDRINUSE: address already in use :::3000` with exit 1 and no readiness line | Another process owns port 3000 — the port is host-global and hard-coded | Find the owner with `lsof -nP -iTCP:3000 -sTCP:LISTEN` and stop it by pid, or wait for it to exit; a port configuration surface is still outstanding work |
| `Error: Cannot find module 'lodash'` at startup, exit 1 | The manifest declares only `express`, but line 2 requires `lodash` | Install it out of band (`--no-save`) or set `NODE_PATH`; declaring it in the manifest is the permanent fix |
| `Error: Cannot find module 'express'` | The dependency was never installed, or the wrong directory is the working directory | Run `CI=true npm install --no-audit --no-fund` from the repository root and start the file from there |
| `npm ci` exits with `EUSAGE: can only install with an existing package-lock.json` | No lockfile is committed, by design | Use `npm install`; committing the lockfile is outstanding work |
| `git status` shows an unexpected change to `package.json` after installing lodash | The README's install line, run verbatim, makes npm save the dependency into the manifest | Use the `--no-save` form and revert the manifest: it must keep exactly `name`, `version` and the `express` dependency |
| `git status` shows an untracked `package-lock.json` | Any `npm install` writes one | Leave it untracked and out of commits |
| A start looks successful but nothing is listening | Impossible on this release: a bind failure exits 1 with no readiness line | Re-read stdout and stderr — the process will have failed loudly; check the two cases above |
| No test command, lint or CI to run | The repository ships none | The verification steps in this section are the whole check surface; adding an automated suite is the highest-value outstanding task |
